# AGENTS.md

Правила для каждого агента, который работает в этом репозитории. Читай этот файл первым: это карта.

Spec-Driven Company (SDC) одной строкой: истина живёт в написанных спеках, агенты их исполняют, а статус виден без вопросов кому-либо.

## Прежде всего: определи тип задачи

Каждая задача — одного из трёх типов. Реши это до чтения файлов и до любого git.

1. **Разговор.** Объяснить, обсудить, посоветовать. Git не трогать.
2. **Чтение.** Читать файлы, ничего не менять. Сначала обновить `main`, потом читать.
3. **Запись.** Всё, что может изменить репозиторий, включая одну строку в docs. Preflight, свой worktree, никогда не писать в `main`.

## Где живёт истина

- `docs/README.md` — одна страница: что это за проект, какие решения приняты, где что лежит.
- `docs/journal.md` — решения и почему: что решили, что отвергли, чьими словами. Только добавление, новое сверху.
- `docs/<зона>.md` — канон одной зоны: как она устроена прямо сейчас. Одно правило, написано один раз, правится заменой.

Файлы для конкретных инструментов лежат рядом с этим и только дополняют его, никогда не ослабляют: `CLAUDE.md` направляет Claude Code сюда; `CODEX.md` несёт то, что относится только к Codex. Там, где они расходятся с этим файлом, побеждает этот файл.

Пара файлов в корне `docs/` принадлежит всему проекту. Каждая подпапка `docs/` несёт свою пару: `README.md` (сводка папки) и `journal.md` (мышление, которое к ней привело). Новая папка рождается сразу с обоими. Файл зоны рождается с первым правилом зоны; пустых не создавать.

Если правило не записано по адресу, его не существует. «Спроси того, кто помнит» — не адрес.

Три вида истины, три дома. Смысловые решения (что строим, для кого, каким голосом) живут в `docs/`. Соглашения инструментов (линтер, форматтер, версии) живут в своих конфигах; в docs их не копировать. Живые данные и статусы (пользователи, заказы, состояния датчиков) живут в базе; docs описывают, как это устроено, и никогда — что там сейчас.

## Как работать

1. **Работай в worktree.** У каждой задачи свой worktree (отдельная рабочая копия репозитория) в `_wt/`; `main/` руками не правят. Как именно — в разделе Git.
2. **Нет задачи без критерия готовности.** Если нельзя проверить, что задача сделана, спроси. Не начинай.
3. **Спека раньше кода.** Требования, план и дизайн в одном документе до первой строки кода. Для каждой формы в нём — страницы, документа, API, названия — найди, кто решил ту же задачу лучше всех, и возьми их каркас; изобретай с нуля, только если можешь сказать, почему ни один каркас не подходит. План — упорядоченные шаги, а не даты: шаг сделан, когда сделаны шаги, от которых он зависит.
4. **Канон раньше кода.** Правило сначала меняется в `docs/`, потом в коде и тестах, в том же изменении. Никогда «сейчас код, доки потом».
5. **Тесты держат правила.** Правило, которое уже стоило времени или денег, получает тест. Сломал тест — почини, прежде чем сказать «готово».
6. **В зонах риска — готовь, но не выполняй.** См. таблицу ниже. Кнопку нажимает человек.
7. **Отчитывайся о результате, не об усилиях.** Скажи, что сделал, чего не сделал и что не смог проверить.

Каждая задача на запись идёт одними и теми же шагами, в этом порядке. Механика неизменна; шаг 8 — рычаг человека.

| # | Шаг | Что происходит | Тип |
|---|---|---|---|
| 0 | Классификация | разговор, чтение или запись: решается до всего остального | механика |
| 1 | Preflight | в `main/`: status, fetch, fast-forward `main`; уборка worktree влитых задач; новый worktree в `_wt/` от свежего `main` | механика |
| 2 | Правки | только в этом worktree, никогда в `main/` | механика |
| 3 | Проверка | команда проверки из раздела «Стек»; красная — значит не сделано | механика |
| 4 | Коммит | на каждом цельном шаге; только изменения этой задачи, никогда секрет | механика |
| 5 | Push | ветка задачи, никогда `main`; до отчёта, чтобы у человека была живая ссылка | механика |
| 6 | Pull request | код идёт через него всегда; изменение, которое трогает только docs и этот файл, сливается без него | механика |
| 7 | Ревью | перечитать дифф как ревьюер; блокируют три вещи: баг на пути денег, доступов или данных; секрет; поломка того, что работало | механика |
| 8 | Слияние | сливает человек; по слову «ship» агент сливает сам, как только проверка зелёная и не задета ни одна зона риска | автономия |
| 9 | Синхронизация и уборка | fast-forward `main` в `main/`; удалить worktree и ветку — или оставить это preflight следующей задачи | механика |
| 10 | Отчёт | блок из раздела «Отчёт», с живой ссылкой | механика |

## Ответы, которыми человек может пользоваться

- Начинай с того, что получилось и можно ли этим пользоваться. Если результат частичный, назови границу и что она значит на практике.
- Простые полные предложения. Термин, ошибку или статус переводи в практический смысл там же, где они появляются; команды и логи — после, как доказательство.
- Называй, кто действует дальше. Если человеку нужно что-то сделать, дай одно действие, место и ожидаемый результат.
- Отличай подтверждённую поломку от того, что не смог проверить. Непроверенное — не сделано.
- Отвечай на языке, на котором пишет человек; код, команды и имена — как есть.

## Git

- **Раскладка.** Проект — одна папка, внутри две вещи: `main/`, сам репозиторий, чистое зеркало ветки `main` на удалённом сервере, и `_wt/`, по одному worktree на задачу, каждая папка названа по своей ветке. Ветка по умолчанию — `main`; репозиторий, который пришёл с `master`, переименовывается один раз, до всего остального. Рядом с ними в папке проекта лежат два файла-указателя, `AGENTS.md` и `CLAUDE.md`, чтобы агент, открытый в папке проекта, нашёл правила в `main/`. После первой установки в `main/` ничего не правят руками: там только синхронизация и уборка. Каждая задача на запись, включая одну строку в docs, живёт в своём worktree в `_wt/`.
- В `main` попадают только слиянием. Код попадает в `main` через pull request, который сливает человек; если человек сказал «ship», агент сливает сам, как только проверка зелёная (или проверки ещё нет) и не задета ни одна зона риска. Изменению, которое затрагивает только `docs/` и этот файл, pull request не нужен: агент сам сливает его в `main`. Удалённого сервера ещё нет? Те же правила, слияние локально; удалённый сервер и pull request'ы приходят с первым кодом. Единственное исключение из «только слиянием» — первая установка, и она происходит в самом `main/`: репозитория ещё нет? `git init -b main` в `main/`, собрать установку там, один коммит на `main` и сказать об этом в отчёте.
- Preflight для каждой задачи на запись, в `main/`: `git status`, `git fetch --prune` (пропусти, если удалённого сервера нет), fast-forward `main`. Если `main` грязный или опережает удалённый сервер, остановись и скажи об этом. Затем убери worktree, оставшиеся от прежних задач: `git worktree prune`, и каждая папка в `_wt/`, чья ветка влита (исчезла с удалённого сервера, потому что репозиторий удаляет ветку при слиянии; без удалённого сервера — уже содержится в `main`) и чей `git status` чист, снимается командой `git worktree remove`, а её ветка удаляется через `git branch -D` (после squash-слияния git считает ветку невлитой, и `-d` откажет). Worktree с незакоммиченными или неотслеживаемыми файлами остаётся и называется в отчёте; больше семи worktree после уборки — перечисли их в отчёте. Уборка стоит здесь, в начале, потому что сессия, которая делала задачу, обычно уже закрыта к моменту, когда её pull request сливают; следующая задача приходит всегда, значит уборка случается всегда. Затем `git worktree add ../_wt/<ветка> -b <ветка> main` и работай только там: правки, установка зависимостей, проверка, dev-сервер.
- Имя ветки: `<агент>-<ГГГГ-ММ-ДД>-<тема>`, например `codex-2026-09-02-signup-form` или `claude-2026-09-02-signup-form`. Папка worktree носит то же имя.
- Коммить на каждом цельном шаге. Коммит — точка, к которой можно вернуться. В него идут только изменения этой задачи; никогда секреты, никогда чужая незаконченная работа.
- Перечитай дифф как ревьюер, потом запушь ветку и открой pull request. Блокируют три вещи: баг на пути, где движутся деньги, доступы или данные; секрет в файлах; изменение, которое ломает то, что работало. Стиль — не находка.
- После слияния, если сессия ещё здесь: в `main/` сделай fast-forward `main`; удали worktree и ветку. Если нет, это сделает preflight следующей задачи. Настройка репозитория «Automatically delete head branches» включена с первой установки: по ней следующая задача отличает влитый worktree от живого.

## Стек

Из чего сделан проект и две команды, которые нужны каждому агенту. Заполняется при установке, меняется заменой, когда меняется стек. Кода ещё нет? Напиши «none yet» во всех трёх строках; не выдумывай проверку для проекта, в котором нечего проверять.

- Сделан из: [языки, фреймворки, база данных, хостинг, одной строкой]
- Проверка: [одна команда, которая запускает форматтер, линтер, типы и тесты, например: pnpm check]
- Запуск: [одна команда и адрес, например: pnpm dev → http://localhost:3000]

## Проверка

Запускай команду проверки из раздела «Стек» перед каждым коммитом. Красная — значит не сделано, какой бы ни была причина. Предупреждение, которое уже было раньше, — не повод звать человека.

## Зоны риска: готовь, но не выполняй

| Всегда | Сначала спроси | Никогда |
|---|---|---|
| работать в ветке, писать спеку, запускать проверку, отчитываться | всё, что двигает деньги, касается ключей или доступов, хранит или отправляет персональные данные, публикует что-то вне репозитория, меняет настройки продакшена | удалять данные, переписывать чужие изменения, делать force-push в `main`, класть секреты в файлы или логи, просить секрет в чате, печатать секрет из любого файла или вывода команды, оставлять рабочие файлы (скриншоты, логи, дампы) внутри репозитория |

«Сначала спроси» значит: сделай всё до кнопки, потом остановись и передай одну строку с выбором. Не начинай обсуждение посреди работы.

Остановка для человека имеет одну форму. Первая строка — одно действие, начинается с глагола; над ней ничего. Потом где: кликабельная ссылка на точную страницу и клики по порядку (меню, вкладка, кнопка). Потом что написать, когда сделано. Ниже — не больше двух строк о состоянии. Без истории, без вариантов, без «что сделано на данный момент». Если человек ответил скриншотом, первая строка говорит, та ли это страница, вторая даёт следующий клик.

Секрет никогда не проходит через чат. Человек кладёт его туда, где он живёт: в настройки хостинга или в локальный файл с ключами. Агент проверяет по имени переменной и никогда не просит и не печатает значение. `--force` — только на грязном дереве и только с разрешения человека.

## Решения

Решение — выбор, который завтра можно переоткрыть. Оно записывается в `docs/journal.md` как запись с постоянным именем:

```
## 2026-09-02 15:01 · <агент> · ⚖️ signup-without-password · Регистрация только по ссылке из письма

**Решили.** ...
**Отвергли.** ... и почему.
**Слова владельца.** «...»
```

«Слова владельца» — цитата человека. Если человек ничего не говорил и задача пришла вставленным промптом, цитируй его первое предложение.

Правила вокруг решений:

- У одного правила один дом. Другие документы ссылаются на него, а не копируют.
- Канон меняется заменой. Старое правило удаляется в том же коммите; история живёт в журнале и в git.
- Прежде чем предлагать изменение архитектуры, адресов, схемы данных или процесса, прочитай журнал этой зоны. Решённые вопросы не переоткрываются без просьбы владельца.
- «Не сейчас» записывается вместе с событием, которое его вернёт, а не с датой.
- Мышление, которое случилось в чате и не попало в журнал, — незаконченная работа, как код без коммита.

Обнаружил, что действовал вразрез с написанным правилом, — чини причину раньше симптома, сверху вниз: правило не записано — запиши; записано не там — перенеси; записано, но никто не нашёл — сделай его находимым из того места, где начинается задача. «Буду внимательнее» — не лечение.

## Структура

Семь — триггер, а не цель. Меньше сущностей — лучше; уровень должен читаться одним взглядом. Когда на одном уровне появляется восьмой файл, папка, таблица, переменная или скрипт, подними вопрос группировки, и группируй только по смыслу, никогда ради числа. Два файла одного рода на одном уровне — раннее предупреждение: спроси, не хотят ли они папку с `README.md`.

`docs/README.md` остаётся на одной странице. Если он растёт, что-то под ним хочет свою папку.

## Продакшен

Всё, что будет работать без человека, — форма, вебхук, задача по расписанию, интеграция, новый источник данных, — рождается сразу с четырьмя вещами в одном изменении:

1. сам элемент;
2. его канон в `docs/`: откуда приходит вход, куда пишет, известные края;
3. его стекло: место, где виден его статус, страница или строка на существующей странице;
4. его иммунитет: внешняя проверка, которая громко падает, когда элемент сломан («форма отрисовывается и эндпоинт отвечает 200»), а не бизнес-метрика.

Контент и вёрстка без нового потока данных или денег — вне этого правила.

## Отчёт

Каждая задача на запись заканчивается одним и тем же блоком, чтобы человек прочитал его за десять секунд. Строка, которой нечего сказать, опускается.

```
---
🧭 next · один шаг, который сильнее всего двигает проект, и почему
📚 docs · файлы в docs/, на которые опиралась задача, по одному на строку под этой
⚖️ компьют · кто делал работу: <агент> 100% соло, или доли между агентами
✅ merged · <коммит или pull request> · N files +X/-Y
   <путь> +a/-b, по одному на строку; запись журнала несёт своё название: docs/journal.md +12/-0 · «название записи»
🌐 где смотреть
   <адрес>, по одному на строку: локально · превью · продакшен
🛂 паспорт · элемент ✅ · канон ✅ · стекло ✅ · иммунитет ⬜ (только когда что-то будет работать без человека)
⚠️ не проверено · что не смог проверить и почему, или «ничего»
```

Строка git — одна из: `✅ merged · …` · `🔀 pull request #N · проверка зелёная, ждёт человека` · `📝 закоммичено (только первая установка) · <коммит>` · `⛔ заблокировано · почему`. Файлы под ней берутся из `git diff --stat`, никогда из памяти.

## Петля

задача словами → работа → приёмка по критерию → отгрузка → наблюдение → следующая задача

Каждая единица работы — один полный оборот этой петли. Та же петля крутится на любом масштабе: фича, продукт, зона бизнеса, компания. Наблюдение за прошлым оборотом — то, откуда берётся следующая задача.
